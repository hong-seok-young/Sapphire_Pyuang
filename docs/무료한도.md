# 무료 한도 안에서 만들기 (필수 규칙)

제작자 2026-11-17: '무료 한도 안 차게 설계해 줘. 그게 필수 규칙이야. 깃에 md 파일로 적어 줘'.
앞서 정한 것: 2026-11-02 '서버는 무조건 무료', 2026-11-14 '무조건 무료로, 계정 10개 쓰더라도', '기능은 빼지 말고 무료 한도로부터 안정적인 선에서'.

**새 기능을 만들거나 고칠 때마다 이 문서를 먼저 읽고, 아래 '만들기 전 확인'을 거친 뒤에 올린다.**
유료 요금제(Workers Paid 등)는 권하지 않는다. AI(Anthropic API) 비용은 따로라 아끼지 않는다 (CLAUDE.md 'AI 는 무조건 품질').

## 1. 지켜야 하는 한도 (Cloudflare 무료, 2026-11 확인)

| 무엇 | 한도 | 넘으면 |
|---|---|---|
| 요청 하나의 CPU (Pages Functions) | 10ms | 그 요청이 실패 (긴 답이 중간에 끊김) |
| 하루 요청 수 | 10만 | 그날 사이트가 멈춤 |
| D1 하루 읽기 | 계정마다 500만 줄 | 그날 모든 DB 요청이 막힘 (2026-11-14 실제로 막힘) |
| D1 하루 쓰기 | 계정마다 10만 줄 (색인 쓰기도 셈) | 그날 쓰기가 막힘 |
| D1 DB 하나 크기 | 500MB | 쓰기가 막힘 |
| D1 DB 수 / 계정 전체 크기 | 10개 / 5GB | |
| Durable Object (답 받기 일꾼) | SQLite 저장소만, CPU 30초 | |
| 요청 하나의 바깥 요청 | 50번 (폰 알림은 40대씩 나눠 보낸다) | |

하루 기준은 UTC 0시 (한국 9시)에 다시 찬다.
지금 계정: 첫째 계정 = 계정·글·사진(DB 1)과 사이트, 둘째 계정 = 사용 기록(`sapphire-log-r1`, 일꾼 `web/logworker`).
GitHub Actions 는 공개 저장소라 무료다 (무거운 일은 여기로).

## 2. 설계 규칙

### 읽기 (가장 자주 넘침)
- 큰 표(activity, alerts, level_log, board_*, chat_msgs, official_*)를 사람·시간·글로 찾으면 **반드시 색인**을 쓰고, 만든 쿼리는 `EXPLAIN QUERY PLAN` 으로 `SCAN 표` 가 없는지 본다.
  필요하면 색인을 같이 만든다 (`schema.sql` 맨 아래 색인 묶음, 사용 기록 DB 는 `server/logdb.ts` LOG_SCHEMA).
- 시간으로 거르고 사람으로 묶는 activity 쿼리는 `INDEXED BY activity_at` (2026-11-14 사고: GROUP BY 때문에 색인을 통째로 훑어 한 번에 1.3만 줄).
- `WHERE … IN (부분 쿼리) ORDER BY id DESC` 처럼 큰 표를 번호 순으로 훑으며 거르는 모양을 피하고, 작은 쪽(사람의 대화·글)부터 색인으로 들어간다 (`CROSS JOIN` 으로 차례를 정한다. 예: `server/actChat.ts` chatFeed).
- 여럿이 같은 숫자를 보는 무거운 셈(대시보드, 통계, 검색)은 Cloudflare 캐시에 몇 분 둔다 (`functions/api/activity.ts` `cached`, 아이모 소식 찾기 10분).
- 지난 날의 셈은 한 번만 하고 요약 표에 적는다 (`server/actDash.ts` act_day_*). 오늘 것만 그때그때.
- 목록은 늘 `LIMIT` 과 '더 보기'(번호로 이어 읽기). 한 번에 수백 줄 넘게 주지 않는다.
- 화면이 주기적으로 묻는 것(polling)은 보이는 동안만, 2분 이상 간격이 기본 (🔔 1분, 새 글 2분, 지금 접속 중 30초 + 캐시 30초).

### 쓰기
- **누를 때마다·볼 때마다 한 줄씩 쓰지 않는다.** 화면에 모았다가 한 줄로 보낸다.
  예: 사용 기록의 누른 단추는 한 화면에서 누른 것을 모아 한 줄 (`src/activity.ts` startTapLog: 화면을 떠날 때·다른 앱으로 갈 때·60개·2분. 하루 200줄 상한은 2026-11-19 제작자 '200개 한도 없애'로 뺐다).
  시뮬레이터 코인 1.5초 모아 보내기, 운영진 때리기 3초 모아 보내기, 헬스 루틴 하는 중 저장 1.2초 모아 보내기도 같은 생각.
- 잦은 자동 저장(콤보 실시간 저장, 하는 중인 운동, 시뮬레이터)은 사용 기록에 남기지 않는다 (`functions/api/_middleware.ts` 의 빼는 목록).
- 모두에게 가는 알림은 사람마다 한 번(본캐), 폰 알림은 40대씩 나눠 보낸다 (`push_queue`).
- 기록은 지우지 않는다 (CLAUDE.md '기록은 평생'). 그래서 쌓이는 속도를 늘 어림하고, 사용 기록은 둘째 계정·DB 돌려쓰기로.

### CPU (요청 하나 10ms)
- 큰 글을 서버에서 풀거나 바꾸지 않는다: 챗봇 답은 SSE 를 그대로 넘기고, 공식 글 받기·그림 읽기·To do 정리는 GitHub Actions 가 한다.
- 오래 걸리는 일은 답 받기 일꾼(Durable Object 알람)이나 Actions 로.

### 계정 나누기
- 한 계정의 하루 읽기·쓰기가 늘 50% 를 넘으면 기능을 끄지 말고 무거운 것을 다른 무료 계정으로 옮긴다 (2026-11-14 사용 기록을 둘째 계정으로 옮긴 방법: `server/remoteD1.ts`, `web/logworker`, `web/scripts/log-worker.mjs`).
- **한도에 가까워져도 기능을 저절로 끄거나 빼지 않는다** (제작자 2026-11-14 '기능 떨어트리지 마'). 읽는 양을 줄이고(색인·캐시) 계정을 나눈다.

## 3. 감시

- `.github/workflows/d1-guard.yml` (15분마다, `web/scripts/d1-guard.mjs`): 계정마다 오늘 읽은 줄/500만, 쓴 줄/10만을 재서 50% · 70% · 90% 를 넘을 때마다 앱개발자에게 알림.
- 알림이 오면 `.github/workflows/d1-usage.yml`(손으로) 로 어떤 쿼리가 얼마나 읽었는지 보고 고친다.
- 새 기능을 연 다음 날 d1-usage 로 그 기능의 쿼리가 읽은 줄을 한 번 본다.
- DB 크기: 사용 기록 화면 '통계 > 저장소', DB 1 이 70%·90% 를 넘으면 알림.

## 4. 만들기 전 확인 (새 기능마다)

1. 하루에 몇 번 불릴까? (사람 수 x 하루 쓰는 횟수) — 사람 수는 사용 기록 '통계'의 들어온 사람으로 어림하고 넉넉히 두 배로 잡는다.
2. 한 번에 몇 줄 읽고 몇 줄 쓸까? `EXPLAIN QUERY PLAN` 으로 색인을 타는지.
3. 1 x 2 가 하루 읽기 500만 · 쓰기 10만 의 **5% 를 넘으면** 모으기·캐시·요약 표·다른 계정 중 하나로 줄인다.
4. 화면이 저절로 묻는가? 보이는 동안만, 간격은 충분한가?
5. 서버에서 큰 글을 풀거나 바깥 요청을 여러 번 하는가? (10ms · 50번)
6. 만든 뒤 로컬에서 재 보고, 연 다음 날 d1-usage 로 확인.

## 5. 어림 예 (2026-11-17, 사용 기록 개편)

- 누른 단추: 한 화면에 한 줄 -> 화면 기록과 비슷한 수. 2026-11-15 사용 기록 쓰기는 하루 약 1,600줄(둘째 계정 10만의 1.6%)이라 두 배가 돼도 3~4%.
  기기마다 하루 200줄 상한은 2026-11-19 뺐다 (제작자 '200개 한도 없애': 도감 완료 체크처럼 한 화면에서 수백 번 누르면 그날 기록이 끊겼다).
  한 줄에 60번까지 모으므로 1,600번 눌러도 30줄쯤. 감시는 d1-guard 알림(둘째 계정 쓰기)로.
- 챗봇 질문과 답: 계정 DB 의 대화를 색인(chat_threads_user, chat_msgs_thread)으로만 읽는다. 기록 화면 한 번(질문 줄 수십 개)에 수백 줄, 챗봇 칸 한 번에 30쌍.
- 기록 화면 한 번에 사용 기록 200줄 (둘째 계정에서).

## 6. 어림 예 (2026-11-19, 화면 기록 서버 저장 `user_kv`)

- 무엇: 이 기기(localStorage)에만 두던 사람의 기록(도감 수치, 배지 본 때, UPDATE 본 메뉴, 튜토리얼 본 메뉴, 최근 검색어, 배경 설정, '다시 안 보기')을 계정 DB 에도 (`src/userSync.ts`, `functions/api/kv.ts`).
- 읽기: 앱을 열 때 한 번 `SELECT … WHERE user_id = ?`(기본 키 색인), 한 사람 20~40줄. 하루 60명 x 5번 x 40줄 = 1.2만 줄 (하루 500만의 0.2%).
- 쓰기: 바뀐 열쇠만 3초 모아 한 번. 글·물건을 열 때마다 바뀌는 배지 본 때가 가장 많다. 하루 60명 x 30줄 = 1,800줄, 많게 잡아 5,000줄 (하루 10만의 2~5%).
  줄 하나에 행 쓰기 + 기본 키 색인 쓰기라 두 배로 잡아도 5% 안팎. 넘칠 기미가 보이면 배지 본 때(sapphire.newsThing)의 모으는 시간을 늘린다.
- 크기: 한 사람 300줄 · 한 값 6만 자까지 (서버가 막는다). 배지 본 때는 14일 지난 것을 지워 몇 KB.
